## Backend at a glance

- **Repo:** https://github.com/shreyasananth-3/dutta-messenger-.git
- **Tech:** FastAPI + PostgreSQL + Redis + MinIO (S3-compatible).
- **Base URL (local):** `http://localhost:8000`
- **API prefix:** `/api/v1`
- **WebSocket:** `ws://localhost:8000/api/v1/ws` (not live yet — lands in backend Stage 4d / `ENABLE_CHAT=true`).
- **Interactive docs:** `http://localhost:8000/docs` (Swagger UI), `/redoc`, `/openapi.json`.
- **Health probe:** `GET /health`.

### The single source of truth for every endpoint

The backend repo ships:

- `docs/ui-contract/README.md` — how the API works at the system level (envelope, versioning, auth flow, pagination, rate limits, error codes).
- `docs/ui-contract/{module}.md` — per-module contracts with real request/response JSON copied from tests.
- `docs/ui-contract/openapi.json` — machine-readable spec, regenerated by `make openapi-export`.
- `docs/ui-contract/postman_collection.json` — importable for click-testing.

**Rule for Claude:** when asked to integrate with an endpoint, read the relevant file under `docs/ui-contract/` in the backend repo **before** writing Dart code. Do not guess at URL paths, field names, or error codes.

## Non-negotiable rules when writing Flutter code against this API

### 1. Response envelope

Every response is one of three shapes — parse strictly against them.

```jsonc
// success (single):   { "data": { ... } }
// success (list):     { "data": [ ... ], "pagination": { "has_more": bool, "next_cursor": string|null, "limit": int } }
// error (any non-2xx):{ "error": { "code": string, "message": string, "details": object } }
```

Put these in typed Dart models. Example:

```dart
sealed class ApiResult<T> {}
class ApiSuccess<T> extends ApiResult<T> { final T data; final Pagination? pagination; ... }
class ApiError<T>   extends ApiResult<T> { final String code; final String message; final Map<String, dynamic> details; final int status; ... }
```

Never inspect `error.message` for logic — switch on `error.code`.

### 2. Auth

- **Login** → stores `access_token` (30-min) and `refresh_token` (7-day) in `flutter_secure_storage` (iOS Keychain / Android Keystore). **Never** `SharedPreferences` for tokens.
- **Every protected request** sends `Authorization: Bearer <access_token>`.
- **On 401 `UNAUTHORIZED`:** call `/api/v1/auth/refresh` with the refresh token, retry the original request **once**. If the retry also fails → clear storage, navigate to login.
- **On `change-password` success:** existing refresh tokens are revoked by the server. Force a fresh login.

### 3. Cursor pagination only

Never send `?page=N`. Always `?cursor=<next_cursor>&limit=50`. Stop when `has_more` is false.

### 4. Rate limits

HTTP 429 with `Retry-After` header. Implement exponential backoff (base 500ms, cap 8s), max 3 retries, then surface to user.

### 5. Correlation IDs

Every response has an `X-Request-ID` header. On any error log path, include it in:
- `console.log` / `debugPrint`
- Crashlytics / Sentry breadcrumbs
- Any support ticket

Backend engineers grep logs by this ID.

### 6. UUIDs everywhere

All IDs are UUID strings (`4bfb3d2c-5f28-4a2a-9e5d-3dc7e9b1f1c4`). Never assume integers or short strings. Use a typedef `typedef UUID = String;` for clarity.

### 7. Timestamps

All timestamps are **ISO 8601 UTC** (`"2026-04-18T14:32:10.123Z"`). Parse with `DateTime.parse(...).toLocal()` for display; always send UTC back.

### 8. Feature flags on the backend

Modules default to OFF. If a call to, say, `/api/v1/groups` returns 404 with no data, the module may simply not be enabled in this environment. Check the `enabled_modules` list on startup (logged by the server) or the backend's `docs/ui-contract/README.md` status table.

## What Claude-in-Flutter-repo should do for a new feature

Follow this recipe for **every** backend-facing feature:

1. **Identify the backend module** (auth / users / chat / …).
2. **Open** `docs/ui-contract/{module}.md` in the backend repo. Do not skip.
3. **Write or regenerate Dart models** from the JSON examples in that file.
   - Prefer `openapi_generator_cli` against the committed `openapi.json`.
   - Manual models are fine for small surfaces but must mirror field names exactly (snake_case → `@JsonKey(name: ...)` mapping).
4. **Write the repository / service layer** using the shared `ApiClient` (Dio-based, handles 401 refresh + 429 backoff + correlation-ID capture).
5. **Write a widget test** using `mocktail` or `dio_adapter` that asserts the success shape, error-code branches, and 401-refresh path.
6. **Never store secrets** in code or `SharedPreferences`. Only `flutter_secure_storage`.
7. **Every error shown to the user** must surface the correlation ID ("Error · request 4bfb3d2c…") so support can find it.

## Project conventions the Flutter Claude should follow

(Override/merge with your existing conventions in the main CLAUDE.md.)

- **Architecture:** feature-first directory layout (`lib/features/{chat,auth,groups}/{ui,domain,data}`), not tech-first.
- **State:** pick one (Riverpod / Bloc / Provider) and stick with it across features.
- **Networking:** one `ApiClient` singleton wrapping Dio with the interceptor chain below:
  ```
  [request]   → inject Bearer token → inject X-Request-ID echo debug →
  [response]  → parse envelope → typed ApiResult
  [error]     → if 401 then refresh+retry once, else map to ApiError
  ```
- **WebSocket client:** one `ChatSocket` singleton. Reconnect with exponential backoff, resume-from-cursor using the last `message_id` seen. Detailed event catalogue is in the backend's `reference-docs/modules/chat/WEBSOCKET.md`.
- **Persistence:** Isar or Drift for messages and groups (offline-first). Secure storage ONLY for tokens. User profiles are cached in memory + Isar.
- **Error UI:** never show raw `error.message` to the user; map `error.code` to localized strings.
- **Logging:** use `logging` package with levels; on release builds, pipe warnings+ to Sentry. Always include `X-Request-ID` when logging HTTP errors.
- **Testing:** `flutter test` for unit/widget, `integration_test` for end-to-end against a local backend (`make run` in the backend repo).

## Regenerating the OpenAPI client

```bash
# 1. In the backend repo:
cd /path/to/dutta-messenger
make run                       # keep running in one terminal
make openapi-export            # in another terminal — writes docs/ui-contract/openapi.json

# 2. In the Flutter repo:
dart pub global activate openapi_generator_cli
openapi_generator_cli generate \
  -i /path/to/dutta-messenger/docs/ui-contract/openapi.json \
  -g dart-dio \
  -o lib/src/api
```

CI should run this and fail if the generated client drifts from committed code, preventing silent contract breaks.

## When in doubt — ask the backend, don't invent

If an endpoint's behaviour is unclear:

1. Check `docs/ui-contract/{module}.md`.
2. Check `reference-docs/modules/{module}/MODULE.md` (design-level).
3. Check `reference-docs/API_STANDARDS.md`.
4. Only if none of the above answer it — open a GitHub issue on the backend repo. Don't guess in code and hope.
